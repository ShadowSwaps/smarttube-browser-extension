# Usage and quality workflow

Adopted for SmartTube Browser on 17 October 2026 at the human's request. These practices adapt the focused ownership of Building REA Companion, the source-bound acceptance of Calendar planning and coordination, and the evidence/usage discipline of GameVault Coordinator. Their project-specific permissions/automations do not transfer.

## Coordinator and task ownership

### Task status and human routing

Lead every task-chat checkpoint/final reply with truthful status, concrete outcome and relevant brief verification, limits and evidence links. Close with a natural sentence: stay in this task chat or return to **SmartTube Coordinator**, why, required human action/input or none, responsible owner and return condition. Use sentence case; bold a key status or destination when useful.

Use Completed only with all scoped obligations and mandatory gates resolved, including required checks/review. Ready for review is intermediate and retains ownership and pending gates. Still working means actual authorized remaining work; it cannot override a stop. Checkpointed means stopped and unaccepted; an exhausted budget requires explicit human authority for further bounded work and review allowance. Human routing alone changes no ownership, acceptance, completion, idle confirmation or archive permission.

- **Completed:** “[Task] is implemented and verified; required tests and review passed, and the final handoff is saved. Return to **SmartTube Coordinator** for final closure and next-task decisions. No further action is needed in this chat. This chat stays open until the coordinator verifies completion and idle status for any authorized archive.”
- **Still working:** “[Finished result] is ready; [specific authorized work] remains. Stay in this task chat while I finish [checks/repairs]. No action is needed from you right now. I’ll tell you when to return to **SmartTube Coordinator**.” If human input is required, replace the no-action sentence with that specific request.
- **Ready for review:** “The candidate and evidence are ready; required review is pending. Return to **SmartTube Coordinator** for review/status. No action is needed in this task chat while review runs. I retain scoped repairs and will resume only for authorized findings or required input.”
- **Checkpointed:** “[Blocker/stop] remains; the task is not accepted. Return to **SmartTube Coordinator** for your decision on leaving it checkpointed or explicitly authorizing further bounded work. This task chat stays open, with repairs stopped and ownership retained.”

An intermediate review return to the coordinator retains task repairs and open gates. Keep human destination distinct from implementation ownership/final closure.

The human adopted coordinator/task routing and bounded review on 17 October 2026. SmartTube Coordinator retains scope, acceptance/publication decisions and closure bookkeeping. Each substantial authorized feature/coherent policy task uses a fresh selected-source chat and [saved handoff](TASK_HANDOFF_TEMPLATE.md), rather than a full-history fork. Small repairs remain in the owning task. Fresh tasks share account allowance; no usage saving is claimed from changing chats.

This authorizes scoped task-chat creation/coordination and recoverable archive of verified completed tasks. It does not authorize agents, unrelated external messages, schedulers, runtime automation, permanent deletion, worktree cleanup or the next feature. Keep every action within human scope/publication authority. Task workers do not create other chats or send cross-chat updates unless explicitly authorized by their handoff; use saved results and completion events where available. Keep the coordinator open.

Only one implementation owner writes this checkout at a time. Record the reservation before dispatch; transfer only after the prior owner saves source/evidence, stops writing and reconciles uncertain tool results. The owner handles implementation, self-checks, scoped corrections and assigned authorized release verification. Review grants read/review authority, never automatic writing authority. Waiting for review is an intermediate handoff; it neither closes the task nor frees it to start another feature.

Before task proposal/dispatch, state actual/recommended model, reasoning and speed, with a reason. Use configured defaults unless a specific override is authorized; preserve current speed/settings and no additional spending. Mark unexposed values unavailable; invent no setting or claim of change. Recommendations do not apply settings. Another project's model/approval/hold/scheduler policy is selected evidence, not SmartTube authority.

## Work cycle and stopping boundaries

1. Coordinator reads the request, relevant checkpoint and repository state; freezes the bounded result, preserved contracts, acceptance scenarios, affected files, non-goals, authority and stopping boundary. Choose the impact-based [review path](REVIEW_POLICY.md); retain every inherited mandatory gate.
2. Check usage at task start and substantial phase boundaries. Use minimum remaining percentage across all usable windows, including weekly; unavailable values are not zero. Keep existing tools and allowances without paid overage.
3. Save the selected-source handoff, work-item ID and writer reservation. Record intended dispatch destination before delivery and returned chat/acknowledgement immediately after. If delivery is uncertain, inspect/reconcile the exact destination before retrying; never blindly duplicate a task.
4. Owner implements one coherent slice, runs meaningful focused checks and preserves failures. Inspect the assembled candidate and perform relevant regression, integration and packaging checks. Documentation alone requires no unchanged media runs. Reuse passing evidence only when relevant source/tree, artifact, configuration and environment still match and no new failure or concern invalidates it.
5. Self-review the actual final diff and evidence, then obtain the required non-author review. Keep stable findings and pass counts; allow the initial review plus at most two repair-and-verification rounds. At an unresolved limit, recurring repair, scope growth or unresolved dispute, checkpoint under the review policy. Only explicit human authority can add bounded review/repair rounds; the coordinator may resolve frozen-requirement interpretation or choose a checkpoint/backlog option, but cannot extend the budget.
6. Record the exact result and pending actions. Before acceptance, coordinator inspects the exact candidate, actual review and evidence. Publish only with applicable human authority; verify destination/artifact; checks do not grant permission. Keep scoped fixes, required inputs and authorized publication verification pending until resolved.
7. Save final return evidence and confirm the exact task is idle. Coordinator verifies closure and archive eligibility below. Do not start another feature from an implementation-complete handoff.

At <=10% remaining, assess whether all remaining authorized scope, required checks, delivery and checkpoint overhead can finish above 4%. Continue only on a supported positive assessment; otherwise checkpoint and stop substantive work. At <=4%, checkpoint and stop. Never omit checks to fit quota. Reassess after scope/usage changes; a short-window reset does not restore weekly allowance. Local stops grant no continuation/scheduler authority. Explicit human pauses and required inputs remain in force.

## Evidence and acceptance

| Record | Required contents |
| --- | --- |
| Change brief | Stable work-item ID, authorization, baseline/dirty state, intended and preserved behavior, affected components, non-goals, acceptance and stopping boundary |
| Test result | Candidate identity, scenario/command, relevant configuration/environment, exit/outcome, evidence location |
| Review | Chosen path/reason, inherited gates, reviewer identity/authorship, self-review or non-author method, findings ledger, cumulative passes and dispositions |
| Release | Exact source and artifact identities, relevant accepted checks, authorization, verified publication result |
| Installation | Normal or disposable profile, installed source/version, observed behavior, conflicts and unperformed cases |

Use distinct coverage labels: implemented; verified under fixtures; verified on a live site; accepted in the normal profile; partially verified; failed; or unrun. Test totals support stated scope, never universal compatibility. Preserve historical failures and source comparisons. Do not silently replace an earlier source baseline to make a check pass.

## Context and ownership

Search and read selected evidence first. Summarize large tool results before active context; retain full evidence for necessary deeper review. Batch independent reads; sequence edits, approvals and dependent acceptance steps.

Use short checkpoints with source/evidence links and exact remaining work. Load this workflow at task start and ownership/closure boundaries, the review policy for review selection and finding repair, and the template for dispatch/return. Avoid repeated detailed policy/history reads when unchanged selected evidence suffices. Preserve this chat's isolated graph; resolve its session from hook context or `CODEX_THREAD_ID`, never another chat or project recency. Track only relevant files and keep changed/pending semantics visible; refresh failure does not block the task.

Monitor with compact completion/attention waits and the last returned cursor. Bound calls to 60 seconds for actionable user steering and usage boundaries. Do useful independent work when available; do not narrate unchanged snapshots or poll usage while idle. Read deeper evidence on a meaningful change or for acceptance. This creates no automatic wakeup or extra monitoring chat.

## Private ledger and closure

Use ignored `.investigation-tools/workflow/` for the task/archive ledger, per-item handoffs, findings and evidence indexes. `.gitignore` already covers this directory; public policies contain the procedure, not personal data or full histories. Keep stable IDs and evidence links instead of duplicate evidence. Each task entry records coordinator/task identities, authorization, baseline/current source, owner/writer state, model/reasoning/speed disclosure, last usage, review path and gates, cumulative passes, findings path, coverage, publication state, exact next action/destination and return condition. Explicitly mark unavailable fields.

Separate archive eligibility from execution. An archive entry needs the exact task ID/title, accepted scope/commit/artifact, saved final handoff/evidence, reviewer and coordinator acceptance, publication status and evidence (or why not required), confirmed idle state, no pending scoped actions, authorization and actual recoverable archive outcome/reference. Preserve checkpointed tasks and their failures; do not archive them as completed. This manual ledger is no enforcement engine.

The task retains corrections while coordinator review/publication is pending. Return to SmartTube Coordinator for closure only with all pending scoped actions resolved. Implementation finished, a commit, a passing count or a finished turn alone cannot establish closure. Missing mandatory review, requested installation, human input or authorized release verification blocks closure. A separately deferred enhancement or unrequested installation does not. Record that distinction. At the original workflow-documentation checkpoint, 0.3.0 normal-profile acceptance was separately pending and was not a gate for that documentation task; the subsequent [user-reported acceptance](VALIDATION.md#user-reported-normal-profile-acceptance) does not change these closure rules.

Coordinator archives only the exact verified completed/idle task after inspecting saved evidence and required publication. No permanent deletion or worktree cleanup is included. Keep the coordinator open. On tool failure/uncertain state, record archive pending and reconcile before retrying; do not claim archival success from intent alone.

## Current normal-profile acceptance

### Default review environment

Routine testing and visual review use the installed Brave executable headlessly through Playwright, in an isolated workspace profile. This avoids desktop mouse/keyboard input, letting the human keep using their computer. `scripts/browser-test.mjs` uses controlled fixtures; `scripts/live-smoke.mjs` uses a public, signed-out live video. Both already use disposable profiles under `.local`; screenshots and reports go under ignored `test-results`. Preserve prior evidence before reruns overwrite those output names. Close only browser contexts owned by the test.

All test-owned Brave processes must launch with `--mute-audio`, including process restarts and ad hoc reviews. Both shipped test launchers explicitly set it. Playback timing/controls remain testable without sound output. Do not achieve silence by changing system volume or personal browser audio settings.

The isolated fixture route was exercised again on 17 October 2026 for this background-review requirement: all 15 checks passed, including a restart of its own browser process. That run used no native desktop automation. This does not resolve the normal-profile saved-speed failure.

A separate visible Brave window shares the Windows desktop and can interrupt input. Headless review is the default; use the human's normal profile only for explicitly requested acceptance scenarios. Headless test profiles lack their other extensions/account. A future representative compatibility profile should install only selected public test extensions and reproduce explicit settings, without copying personal browser data. The clean fixture pass establishes neither its setup nor compatibility.

## Workflow changes adopted

| Practice | Status | Benefit and quality condition |
| --- | --- | --- |
| Bounded work, one owner, concise evidence reads | Implemented in project guidance | Less duplicated context and work; full required evidence remains accessible |
| Usage checks and conservative checkpoint thresholds | Implemented in project guidance | Avoids paid overage and unfinished verification near exhaustion; no checks are removed |
| Validation reuse tied to unchanged inputs | Implemented in project guidance | Avoids redundant runs while invalidating affected evidence after real changes |
| Separate fixture, live-site and normal-profile coverage | Implemented in project guidance | Prevents broader acceptance claims than actual observations support |
| Reviewer identity and performed method | Implemented in project guidance | Makes self-review and genuinely independent review distinguishable |
| Coordinator, fresh scoped tasks and completion-based recoverable archive | Adopted manual procedure | Selected-source handoffs and verified closure; one writer, no automatic next feature or premature archive |
| Impact-based non-author review and bounded repair loop | Adopted manual procedure | Comprehensive first pass and at most two repair rounds; blockers and mandatory gates remain visible |
| Private task/finding/archive ledger and handoff template | Defined; filled per task | Preserves source, authority, review counts and exact next action without duplicating history |
| Shared quota daemon, automatic chat creation, schedulers and model changes | Deferred | Manual coordination adds no runtime infrastructure or setting changes |

These rules define intended procedure; they prove neither future compliance nor a passed application security audit.
